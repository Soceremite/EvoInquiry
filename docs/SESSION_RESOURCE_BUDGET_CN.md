# 每个 session 一份资源预算表

资源表最初随 **EvoInquiry 1.6.2** 发布；首步计时、动态硬件检查、停止确认与续跑修正属于 **1.6.3**。本页保留各开发阶段记录，当前验收状态见 [1.6.3 审查与修复记录](AUDIT_1_6_3_CN.md)。

EvoInquiry 在首次安排需要计算或存储资源的研究时，为当前 session 初始化唯一的
资源表。先展示目标主机的资源状态，让用户选择：

| 选项 | 设置 |
| --- | --- |
| 最大可用（默认） | 可见且允许使用的本机 GPU；允许符合资源条件的同卡多任务；CPU、内存、存储按可用容量；单任务 12 小时内自动放行 |
| GPU 独占（涉及 GPU 时） | 其余设置相同，GPU 需要空闲，由原调度器确认分配 |
| 自定义 | 指定 GPU ID/UUID、共享方式、时长、内存和存储额度等 |

初始化不等于已经替用户选择。用户选一次，后续规划、实现、执行、调参、对比实验
与 Goal 续跑都复用这一份表；不再逐个询问是否批准 90 分钟。若用户先前已经明确
选择了相同设置，直接记录该选择。只有超出表内范围才需要新的选择。
单次作业的一核、128 MiB 等需求只是作业估算，不能自动当成用户选择的会话额度；
首次选项默认推荐最大可用，具体作业仍按足够完成任务的资源安排。

唯一记录位于 `<project>/.ei/resource-sessions/<session-id>.json`，表格由该记录
渲染。其他 skill、计划、交接文档只引用它，不复制另一套预算。重连和上下文压缩
保留同一 session ID；新的 session 重新初始化、选择。跨项目时保留原来的表格
所有者与路径。用户更新额度时修改同一份表，保留修订号；不能借更新表格重置
已有实验的有限预算、账目或停止请求。

普通的“先做实验计划、暂不运行”请求，在可写会话中仍要初始化资源表并提供首次
选择，收到回复后再编排依赖资源的详细计划；这不会初始化实验运行环境或启动训练。
只有宿主真正的 Plan 模式或其他
只读限制才采用只读检查，并明确保留待初始化状态。

## 真正用于安排与派发

| 检查 | 安排实验前 | 实验真正启动前 |
| --- | --- | --- |
| 表格 | 读取当前 session 的用户选择和修订号 | 重新读取，不能沿用旧额度 |
| GPU | 确认可用设备、各卡总/已用/剩余显存及利用率 | 重新检测；逐卡检查预计新增峰值，并汇总总显存占用 |
| 同卡多任务 | 判断是否允许共享，估计所有并发任务需求 | 服从现有调度器、租约及任务分配；记录比较环境 |
| CPU / 内存 | 检查 CPU 配额、当前可用内存和任务峰值 | 重新检测，包含数据加载器、缓存、优化器等占用 |
| 数据集 | 复用已有缓存，估计下载、解压及额外副本 | 根据实际目标文件系统剩余空间检查新增峰值 |
| 权重 / 断点 | 采用既有保留策略，考虑完整新保存和并发保存 | 同时检查权重、恢复点、临时文件与保留空间 |
| 训练时长 | 从首个实际训练 step 开始，准备阶段另计；表内任务直接安排 | 保留单次训练累计时间及另行明确约定的总墙钟期限 |

“最大可用”是授权上限，不要求用满所有资源。持续 Goal 不新增总时长窗口；多个
表内任务累计超过 12 小时不等于必须续批。用户原有 GPU 限制、资源额度、宿主
Plan/Goal 规则、科研审查、实验公平和存储保留规范继续有效。既有付费服务额度
沿用原授权；默认不新增购买。

资源不足与需要审批是不同状态：显存或磁盘暂时不够时，等待、减少并发或调整
安排即可；不能将一次资源等待直接判为整个 Goal 阻塞，也不能申请后就忽略物理
容量。普通预算检查不打断已在运行的健康训练。

## 单次实验提醒与实际审批额度

时长按独立实验分别核算，例如固定方法配置和 seed 的一次训练；不把多个任务的
顺序耗时相加，作为整组比较或 Goal 的时限。计时从正式进入首个实际训练 step
开始，工程准备、环境配置与下载不提前消耗训练额度；这些阶段的硬件和存储仍需
核算。续训保留已耗训练时间，排除重新准备的间隔。多任务同时运行仍要汇总并发显存、
内存和存储峰值。完整对比组可作为一次回顾单元，这是另一种计数。

同一张表分别保存提醒阈值和真正的自动审批上限。例如已选择单次 12 小时额度，
希望两小时提醒一次，对应自定义设置：

```json
{"auto_approve_job_seconds": 43200, "job_notice_after_seconds": 7200}
```

两小时处提示，不机械中断。超出半小时或预计完整实验需要 3.5 小时，只要仍在
已选 12 小时额度内，就不需要新审批。不能把“不到一小时可以继续”的宽容描述
推导成三小时的硬审批线。最大可用配置仍为单任务 12 小时，默认没有附加提醒；
旧表保留原有额度。修改提醒不会扩大额度，也保留同表其他设备与资源限制。

预计超过提醒阈值或运行达到阈值时，原监控/执行者发出一次继续/停止的非阻塞弹窗，
注明任务、耗时、剩余估计与授权边界。未回复按此前的明确授权继续监听，不结束
本轮专等回复，不把 Goal 标成 blocked，也不把“弹窗已提交”写成“用户已同意”。
若宿主弹窗本身会阻止续跑，则使用普通提示继续监听；skill 无法改变宿主的 UI
机制。用户选择停止时，由原执行者保存恢复点并停止对应实验，核验退出。

`duration --elapsed-seconds <秒数>` 只读返回建议，不更改表格或直接控制进程。
`NOTICE_CONTINUE` 表示表内已授权；`--response continue|stop` 只记录实际收到的
选择。继续回复不扩大额度，重启、重试和续训不清零同一实验的已耗时。超出真正的
自动审批额度时，需要具体例外；显卡、内存、存储、付费和另行明确约定的期限
仍然有效。主动终止进程还需要用户明确同意，或此前明确授权的具体自动停止条件；
额度表、回顾 STOP、默认超时和未回复的提示都不是这种授权。执行者需在启动前
设置获准上界并预留保存时间；新策略不会
自动覆盖已冻结执行或未接入的旧启动器。

## 使用接口

```text
python <package>/tools/resource_budget.py --root <project> --session <id> init
python <package>/tools/resource_budget.py --root <project> --session <id> select --preset maximum --selected-by <用户选择的记录>
python <package>/tools/resource_budget.py --root <project> --session <id> check --stage plan --markdown
python <package>/tools/resource_budget.py --root <project> --session <id> check --stage launch --request <需求.json> --markdown
python <package>/tools/resource_budget.py --root <project> --session <id> duration --elapsed-seconds <单次实验已耗秒数>
```

`CODEX_THREAD_ID` 存在时可省略 `--session`。其他宿主需要传入稳定的会话身份。
`show` 查看同一份表，`check` 会重新读取资源；`--read-only` 不写入状态，适用于
只读规划/监听。派发需求示例（字节数是新增峰值，主机名必须来自实际探测）：

```json
{
  "host": "actual-execution-host",
  "job_seconds": 5400,
  "cpu_cores": 4,
  "ram_bytes": 8589934592,
  "gpus": [{"id": "0", "peak_bytes": 12884901888}],
  "storage": [{
    "path": "/absolute/output-or-data-path",
    "dataset_bytes": 10737418240,
    "weight_bytes": 2147483648,
    "checkpoint_peak_bytes": 4294967296,
    "other_bytes": 1073741824,
    "reserve_bytes": 2147483648
  }],
  "new_spend": 0
}
```

同一文件系统上的多个目录合并计算峰值，避免把一份剩余空间重复分配。已存在的
数据与权重包含在磁盘已用量中，不再作为新增数据重复计费；各目录的现有占用
由数据/权重所有者提供已有清单或针对性测量，不自动扫描整个数据盘。

冻结执行配置通过 `resource_budget.session_id` 与 `resource_budget.request`
绑定该表。已有实验启动器在环境核验后执行实时检查，未通过则保持任务未启动；
同一 session 跨项目时，绑定原表的绝对 `table_root`，避免创建第二份表。当前
session 已有资源表时，该启动器也会拒绝没有绑定表格的新派发。
队列将表格选择、额度例外与容量不足保留为待处理任务，不消耗未启动训练的重试
次数；环境核验后才出现的资源变化也会通过该执行的检查收据返回等待。
治理队列复用同一入口。其他运行器需要接入相同检查。该工具不替代调度器，不
自动覆盖未绑定的旧启动器，也不承诺 GPU 的原子预留或运行中资源硬隔离。

共享规范：[Session resource table](../skills/shared-references/resource-budget.md)。

## Integration review

这次改动通过所有 skill 已有的共享科研规范接入，不新增 skill 或调度器。会话表
只负责资源授权和实时容量判断；实验方案、公平比较、资源账目、训练终态和回顾
仍由原有所有者负责。旧的未绑定执行保持兼容；当前 session 一旦初始化资源表，
原启动器的新派发必须显式绑定它。

发布清单新增资源检查工具、主线与 Codex 共用规范及本页，保留原有文件排除规则。
`tools/skill-contracts.json` 登记发布清单与队列资源等待的定向变更，
冻结基线哈希保持原值。
测试入口：`tests/test_resource_budget.py` 及原执行、协调、发布与镜像回归。

实际 CPU 实操走通首次待选择、测试用户选择、规划放行、冻结执行、实时资源检查、

## 1.6.3 提醒与续跑修正验证（2026-10-26，尚未发布）

资源、冻结执行、队列、回顾、镜像和包保留回归 196 项通过，零失败。包含两小时
提醒下的 2.5 小时、3 小时和约 3.55 小时自动放行，真实审批上限之外保持待处理，
以及短 CPU 子进程和冻结启动器实操；没有执行这些小时数的完整训练。

隔离的新 Codex Goal 会话使用 `gpt-6.1-sol`：一次用户启动，宿主自动续出第二轮，
无用户提醒回复，监听 210 步真实 CPU 任务约 211 秒并核验自然退出。Goal 在训练
存活时保持 active，终态核验后完成。当前用的是文字提示，未验证原生弹窗交互；
模型与工具延迟使部分观测间隔超过请求的 20–30 秒。

另一原生 Plan 会话保持只读，没有重复询问已选预算，但模型将持续监听请求转成了
规划，并称受到宿主 Plan 指令限制。它只核查一次并交付计划，明确未核验终态。
因此首轮验收**没有证明该宿主 Plan 模式能够持续监听**；所称限制的来源尚未独立确认，
不据此断言所有 Plan 宿主均不支持监听。skill 仍须遵守实际宿主的模式限制。
最初验收脚本误将任务自然结束计为模型观察到终态，已纠正，原始收据保留。

收据位于本地忽略的 `validation/duration-policy/`。初稿曾错误地把软提醒加宽限
转成三小时审批线，该设计已撤销；初稿通过的测试不作为修正后行为的验收依据。

恢复已授权任务时还需核对原生 Goal 状态：普通用户消息、训练成功启动或后台
观察器持续采样，都不证明旧 blocked Goal 已恢复为 active。优先使用宿主提供的
恢复接口，保留原目标和账目；模型工具缺少该操作时说明宿主恢复要求，并在当前
轮次允许的范围内继续工作。不能改数据库、另建 Goal 或提前宣布完成来绕过状态，
也不能把仅采集日志的观察器宣称为持续科研闭环。


1.6.3 版本与发布工作流、镜像及保留契约检查另有 57 项通过；这与前述 196 项存在
重叠，不相加为独立用例总数。最终新增的 Goal 恢复说明和版本号调整晚于原生
CPU 会话测试，不能据此声称原对话已恢复。默认本地源与缓存已更新为 1.6.3
开发版，305 个运行文件与当前源码一致；原生重新扫描识别 89 个该版本的入口，
零扫描错误。1.6.2 缓存和配置已备份，本次尚未 GitHub 提交或发布。

## Continuation scope review

1.6.3 进一步审查发现：外部续跑规范将不确定关卡默认视为人工关卡，旧停滞信号
`pivot=human` 容易被理解为必须等待用户；流水线正文还残留“每次心跳记录发现数”，
与健康任务等待不计入停滞的规则矛盾。公共分析规范的“报告后停止”也未限定独立任务。
这些是指令设计中的隐患，不代表它们都在原会话中实际被调用。

修正后，科研原则统一解释局部停止的范围：子分析完成后回到原任务，回顾由原所有者
执行，计数只建议复盘，不自动修改科研协议或要求人工批准。仅在一次调查完成后
记录一次发现数；监控、等待与回顾本身不产生零发现迭代。旧 `pivot` 返回值和
原有有限预算保留，DSE 的超时仅结束该搜索批次，不结束整个 Goal 或其他训练的监听。
依赖缺失只暂停依赖它的步骤；可行的已授权工作、健康训练的观察继续。

Plan 中明确请求的观察应交给原监听者，在宿主允许的当前轮次只读进行。已有后台
采样可继续运行，但采样存活不证明下一轮 AI 分析已经被调度。当前 Codex 的
[官方 Goal 说明](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)
明确指出 Plan-only 不触发自动续轮；skill 不能通过修改规范改变这一宿主行为。
任何已确认的用户人工关卡、真实资源上限、科研审查和宿主限制仍按原范围执行。

本次局部停止范围、计数、回顾、auto-proceed、包契约与镜像回归 126 项通过；随后
主线 Plan 说明与 Codex 对齐后，包契约和镜像复核另有 52 项通过，两组存在重叠。
新原生 Goal 只收到一次启动，核对已有 `pivot=human` 合成账本后保存阶段分析，自动
续出第二轮，观测同一真实 CPU 任务到 210 步并核验自然退出。没有人工回复，Goal
未在任务存活时阻塞，监控没有追加零发现记录。该测试不等于原生产 Goal 已恢复。
阶段分析的首次保存时点由真实文件创建事件及随后同一子进程存活观测确认；最初
用最终 mtime 判断，因终态后补写报告而误判，原始失败和更正依据均保留。

最后的新原生 Plan 补测通过：真实 readOnly 模式，在同一轮中多次读取实际进度，

## First-step timing, hardware refresh and process consent review

本节继续修正 1.6.3；前述原生 Goal/Plan 证据保留其原受测范围，不冒充本节新代码
已经过模型实测。没有新增 skill、调度器或第二份 session 资源表。

**首步计时。** 单次训练额度与两小时提醒从进入首个实际训练 step 开始，不从规划、
下载、安装、代码准备或 `Popen` 开始。原执行者在已有运行记录中维护首步与终止时间；
重试/续训沿用同一固定配置和 seed 的实验身份，累计历史训练段，排除重新准备的间隔。
训练段内部正常评测与保存不反复重置计时。首条稀疏日志可能已是 step 200，不能据此
冒认首步；旧执行没有可靠事件时如实标为未核实。用户另行明确约定的整轮墙钟期限
仍保留原开始时间和准备耗时，两者分别报告。

`duration --training-clock <JSON> --experiment-id <稳定实验身份>` 只读核算已有执行者
的记录，不替训练框架臆造事件。JSON 含 `schema_version: 1`、`experiment_id` 和
`segments`；每段含唯一 `attempt_id`、带时区的 `first_step_at`、`ended_at`（仅运行中
最后一段可为 null）。空段表返回 `TRAINING_NOT_STARTED`。缺失、重叠、未来时间、
身份不符等记录不能当成已核实耗时；`--elapsed-seconds` 的调用者同样必须提供实际
训练耗时。这个辅助接口不能认证任意调用者提交的“首步”是否真的执行。

**动态硬件。** 安排前和每次启动前都重新探测目标主机，将实测与有效容量保存在
同表 `last_check` 中；记录 GPU UUID/容量、CPU 配额、内存上限等变化。坏卡或
不可读设备不伪装成空闲，另一张可读卡仍可单独评估。最大可用配置跟随当前允许的
设备，显式 allowlist 和数值授权不自动扩大。只读 Plan 检查仅报告，不写表。
需求超过整卡/整机容量时返回 `REPLAN_REQUIRED`；暂时被占用则为 `WAIT_RESOURCE`。
显卡遥测正常不是完整硬件健康认证，仍需实际执行/必要的小探测验证。

训练、评测和保存的新增峰值与余量应分别有依据。固定“空闲 28 GiB”不能代替
测量，训练峰值也不能直接证明评测并发峰值。资源紧张时先等待、调整并发或修订
后续执行的工程条件，不因另一进程占卡而擅自停止它。已冻结运行和历史证据不改写。
接入资源表的队列不再额外受旧的“已用显存小于 500 MiB”筛选阻挡；它仍保留自身
每设备一个在队训练作业的并发约束，外部共享由实际授权和容量决定。资源检查不等于
原子预留，未接入的旧启动器不会自动获得新行为。

**停止确认。** AI 的 STOP 结论先保留证据、暂停对应新派发，并提出该实验的非阻塞
继续/停止选项；没有实际答复则继续监听。不能将默认额度、Goal/Plan、NaN/平台期、
资源争用、超时或控制文件错误解释为用户已授权终止。选择停止后才由原执行者保存
可用恢复状态并执行身份绑定的停止，核验真实退出后释放资源。

`execution_registry.py stop` 要求 `--confirmed-by <实际用户回复引用>`，并绑定快照
及进程记录。`research_control.py stop` 默认只阻止新派发；加该参数才表示用户明确
同意停止相应工作流绑定的在途任务。若用户提前明确授权某种自动停止，在冻结配置
中记录 `stop_authorization` 的 `confirmed_by` 与具体 `conditions`，可选 `timeout`、
`workflow_deadline`、`control_error`、`launcher_error`。不能由 agent 用估算值自行
补造该授权；明确授权的条件不会被另一个未确认的回顾 STOP 遮蔽。

没有停止授权时，执行者对到时或观测异常记录 `process-control-notices.json`，继续
观察。若连观测记录也无法持久化，错误中保留实际 PID 和未中断状态，执行保持待核实；
不伪造终态或释放预留。队列不再自动关闭碰名/残留 screen，部分输出和 OOM 字样
也不能证明活进程已结束。对外部调度器本来就设置的硬期限，必须明确其既有行为，
不能声称本 skill 能撤销它或修改正在运行的冻结所有者。
