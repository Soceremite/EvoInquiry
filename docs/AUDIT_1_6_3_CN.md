# EvoInquiry 1.6.3 全版本一致性审查

审查日期：2026-10-26。对象是当前尚未发布的 1.6.3 工作树，不是已发布的 1.6.2。
当前状态：**10 类已确认问题已修复并完成本地验证；Goal / Plan / 普通会话验收通过。尚未发布，原生 Windows/macOS CI 待执行。**

本次使用 `skill-creator` 和实际安装的 `evo-inquiry:research-guide`，检查公共原则、
Codex 与主线入口、执行工具、队列、恢复和发布检查。结论来自代码、明确的文本冲突与
小规模工程复现；不是另一个模型提供的独立科研评审，也不证明所有宿主中的模型行为。

## 已确认问题

严重程度按实际影响排序：P1 表示应优先修复的控制或结果可靠性问题；P2 表示特定路径的
一致性或接入缺口。文本冲突不等同于已经观测到模型违规；两者分别标注。

### F01 · P1 · 试验超时仍有无条件停止指令

`skills/skills-codex/idea-creator/SKILL.md:31` 和 `:311` 要求超过三小时直接 kill；
`idea-discovery/SKILL.md:38` 也有相同要求。两个入口还将超过两小时的估计标成需要人工
pilot。公共资源规范则允许所选额度内自动推进，且停止进程必须有实际用户确认或已授权的
具体自动条件。主线也保留了这些旧规则。

三小时不能凭一个 skill 默认值变成进程停止授权。小规模 pilot 仍可有有限预算，但应先
缩小实验或返回执行者重新安排；不能把合理的探索规模建议变成新的审批关卡。
这是明确的文本冲突，**本次没有等待三小时让模型实际执行终止**。

修复：保留 pilot 的节制目标，将时长选择、软提醒和停止授权交还共享资源契约与现有执行
所有者；定向更新两棵树中的原条款，避免只在顶部继续添加相反的免责声明。

### F02 · P1 · 准入尾部的回顾或停止状态可能被绕过

`tools/execution_registry.py:633` 在环境验证后重读控制状态，随后在 `:649` 检查资源；
进入 `running` 和创建进程前，没有在同一次受控派发转换中再次验证回顾与停止状态。

实测在资源检查返回前设置新的回顾门或禁止新派发状态，两种情况下 CPU 任务都启动并完成，
对应门仍存在。探针为 `late_reflection_allows_dispatch`、`late_stop_allows_dispatch`。
这不是“回顾不应杀死已在训练的任务”的例外：门是在进程创建前设置的。

修复：让最后的控制准入与派发状态转换具有一致的并发边界，采用既有所有者和明确的锁顺序；
增加资源检查期间及实际派发前发生状态变化的并发回归。只再加一个较早的检查不足以消除竞态。

### F03 · P1 · 正常回顾等待被队列变成失败与 stuck

`skills/experiment-queue/scripts/queue_manager.py:301` 仅把资源准入导致的未启动识别为
`pending`。启动器因回顾门拒绝新派发时，执行记录仍是 `prepared`，没有进程和终态，
`:308` 却返回 `failed_other`；调度器随后将其置为 `stuck`。

探针 `reflection_becomes_failed_queue_job` 已复现“正确拦住启动 → 队列误报失败”。
检查直接调用了实际启动器与队列状态函数，没有运行真实 screen 服务。

修复：使用结构化的暂缓派发结果区分回顾、资源等待、政策选择和真正失败；保留同一 prepared
身份与重试次数，回顾完成后由原队列继续。不能用错误字符串匹配伪造一个训练失败。

### F04 · P1 · 旧队列能将仍存活的进程报告为完成

同一队列脚本 `:311` 仅在 screen 存在时保护存活 PID；`:316` 随后直接根据输出文件判定
完成。screen 消失并不证明训练或其子进程已结束，输出也可能是中间结果。

探针 `missing_screen_with_live_process` 使用真实存活 CPU 子进程、已有部分输出，并模拟
screen 消失，得到 `completed`。该问题属于旧执行路径；具有固定终态记录的路径有更强的
检查，不能把两者混为一谈。

修复：独立于 screen 检查已知 PID 和实际退出证据；未知存活状态保留观察/核对，部分输出
不能充当完成凭据。补充 screen 消失、PID 仍活和 PID 不可确认三种案例。

### F05 · P1 · tee 管道掩盖训练退出码

`run-experiment/SKILL.md:155`、`:180`、`:183` 以及队列脚本 `:258` 的示例/封装使用
`python ... | tee ...`，未保留 Python 的退出状态。

探针 `tee_masks_training_failure` 中 Python 明确退出 7，文档所示 bash 管道退出 0；
启用 pipefail 的对应命令才退出 7。固定执行注册器保存 Python 退出码的逻辑是有效的，
但不能据此保证这些旁路也有效。

修复：在实际拥有管道的 shell 中保留训练退出码，区分 screen 成功启动与训练成功完成；
结果收集仍须核对退出与有效输出，不能只修命令文本而不修消费端。

### F06 · P2 · 首步计时尚未自动接入内置运行监控

`tools/resource_budget.py:396` 能验证首步收据、累计恢复段并排除准备时间。
但 `execution_registry.py:_wait_controlled` 没有调用它，也没有消费训练计时收据；
注册器只在启动前用预计的 `job_seconds` 检查会话额度。计时接口和实际持续监控目前有间隙。

探针 `duration_owner_gap` 在准备后记录实际首步和运行中的收据，预计 0.04 秒、所选额度
0.1 秒，实际训练约 0.3 秒。单独检查返回 `NEEDS_APPROVAL`，执行器却没有相应运行中
提醒。这里**不要求未经同意停止进程**；缺少的是主动检查及提醒/决策衔接。

修复：由原执行或监控所有者使用已有训练计时收据，在原监控节奏内调用检查并去重通知。
保留独立的进程/工作流墙钟，不创建第二个监控器；不能对未接入的旧训练声称已自动计时。

### F07 · P1 · “保存后停止”不能由固定五秒硬杀保证

`tools/execution_registry.py:394` 在 SIGTERM 后最多等待五秒，随后对拥有的 POSIX 组
SIGKILL。停止授权本身不等于一次完整 checkpoint 已经写完。

探针 `slow_cooperative_checkpoint` 中，测试进程已响应 SIGTERM 并开始一个六秒的保存，
仍被以 -9 结束，新保存未完成。已有的旧 checkpoint 保留了，所以结论不是“所有断点丢失”，
而是**不能承诺这次选择会完成一次新保存**。

修复：区分普通终止与协作保存后停止，沿用训练器已有保存/停止接口及完成凭据；按已测保存
时间安排合理等待。若需要强制终止，单独说明范围并取得对应授权，不能默认五秒后强杀。

### F08 · P2 · GPU 准入仍有相反的标准

`run-experiment/SKILL.md:69` 将已用显存小于 500 MiB 当作空闲；
`experiment-queue/SKILL.md:124` 要求波次后显存降到该阈值，`:154` 还要求先获得
`max_parallel` 张空闲卡。共享资源规范却要求按当前硬件和阶段峰值准入；已接入资源表的
队列代码也已经绕过旧空闲筛选。正文会让模型在代码检查之前自行拦住可运行的任务。

另一个独立边界是 `resource_budget.py:460`：独占模式要求已用显存和利用率都严格为零。
合成观测中，利用率为零但存在 8 MiB 基础占用的设备被判为 `WAIT_RESOURCE`
（探针 `exclusive_baseline_occupancy`）；若基础占用持续存在，就始终无法准入。
这不是一次真实 GPU 故障或占用测量。

修复：统一使用现有资源准入结果。独占需结合实际进程/分配状态定义，不能把驱动基础占用
等同于他人训练，也不能仅凭低显存占用就夺取他人的 GPU。并行上限是上限，不是启动门槛。

### F09 · P2 · 飞书必需决策与可选通知的超时含义不一致

`feishu-notify/SKILL.md:115`、`:158`、`:162` 要求超时或不可达时 fail open /
auto-proceed；`research-pipeline/SKILL.md:69` 却明确说用户启用的交互审批必须收到真实
回复。Feishu bridge 返回的是 timeout，不能把它转写成用户同意。

修复：由调用方声明这是可选通知还是必需决策。可选提醒无人回复时在原授权内继续；必需
决策只暂停依赖步骤，继续独立工作与已有监听。发送本身也应有明确投递授权和范围，不能仅
凭机器上存在一个配置文件推断本次获准对外发送。本次没有发送飞书消息或调用远端审批。

### F10 · P2 · 部署正文的凭据与提交范围不够严谨

`run-experiment/SKILL.md:144` 仍称 W&B API key 来自 `AGENTS.md`；`:87` 给出的 git
同步路径直接 `git add -A`、commit、push。前者会鼓励把凭据放进经常提交的项目指导文件，
后者可能把与本次部署无关的现有改动一并提交。公共快照契约要求排除凭据和限定输入。

修复：项目指导文件只保存非敏感配置和凭据来源说明，秘密沿用环境变量或既有凭据管理；
git 同步应核对实际差异与范围，沿用用户已给的提交/推送授权，不能用整库 add 代替文件选择。
本次只检查了这些指令，没有读取实际 key，也没有提交或推送。

## 应保留的合理边界与尚未验证的事项

- 回顾阻止新派发、同时继续观察已经运行的任务，这个划分合理。不能为了修 F03 而取消回顾门。
- 首次会话资源选择需要用户真实选择，是用户要求的初始化，不应与重复预算审批混淆。
- 用户明确设置的 `AUTO_PROCEED=false`、必需审稿与实际硬预算仍需遵守；Goal 不将它们自动取消。
- 独立分析、完整流水线、研究记录和知识库目前有不同职责。`paper-poster` 是兼容转发，不能只按
  名称相似就删除。当前没有充分依据通过新增 skill 或大规模合并入口解决上述问题。
- 公平比较、独立单位/多种子、失败保留、验证集选模、客观解释和主动 case study 的公共规范
  相互配合。本轮未发现必须推翻它们的新矛盾；规范齐全仍不保证每次实际执行都正确。
- Codex 的同家族审稿仍只给 provisional；确定性文件完整性检查不证明科研正确或跨家族接受。
- Windows 停止收据只认证父进程，队列释放租约却主要看父 PID；需要验证有存活后代时是否会过早
  释放。这里是代码支持的待验边界，**没有冒充 Windows 原生复现**。
- `.github/workflows/test-suite.yml` 的 Windows 选择列表还没有纳入新建的
  `tests/test_training_budget_clock.py`。即使该 Windows job 通过，也不能称新计时测试已经
  在 Windows 执行；后续应补上这个测试入口。
- `analyze-results` 顶部仍有“保存报告后 stop the workflow”的绝对句，正文后部与共享规范则要求
  为已授权的长程任务返回证据并继续。应在下一次修订明确结束分析子任务的范围；本次没有新做
  原生模型续跑测试，不能断言此句已经造成某个实际 Goal stalled。
- 远程/多主机表的传递、CUDA UUID 缩写/MIG、嵌套容器配额、真实分布式保存和当前原生
  macOS/Windows 行为未全覆盖。没有据此声称支持被破坏，也没有把本地 CPU PASS 外推为全部通过。
- 已经启动的旧冻结所有者不会因安装新 skill 自动改变其显存门槛、计时或状态；不能为升级
  擅自改写在训输入、重启训练或恢复宿主 Goal。
