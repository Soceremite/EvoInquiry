# Complete the requested research task

Use this reference for analysis, planning, and workflow selection. It clarifies
scope and output density without replacing a selected workflow's required
review, evidence, output, or recovery contracts.

## Analysis and formal claim assessment

Numerical analysis includes interpreting comparisons, identifying confounds,
noting missing metrics, and explaining why a causal interpretation is premature.
These caveats belong in the requested analysis. They do not, by themselves,
request a separate formal claim verdict or reviewer workflow.

If the user authorizes analysis followed by a plan, finish those deliverables
using analyze-results and experiment-plan. Carry the caveats into the controls
and decision criteria. A missing reviewer need not block this independent
preparation; describe its review status accurately in the requested files.

Select result-to-claim when the user requests a formal assessment of whether
results support a research claim, or when the active workflow requires its gate
before the next action. Explicit skill selection takes priority. Once that gate
is required, preserve its prechecks, reviewer requirements, and blocked or
provisional distinctions. Do not replace a required gate with ordinary analysis.

## Useful planning detail

Match detail to the requested decision. A detailed roadmap needs concrete
controls, metrics, splits, run order, failure criteria, and resource assumptions;
it does not need the same rationale or protocol repeated in every block.

Write shared settings once. Use a compact claim-to-experiment table and describe
only each block's differences. Distinguish required experiments from optional
extensions. Mark unknown inputs and estimated budgets explicitly instead of
inventing specifications or expanding speculative branches.

A roadmap is a decision artifact. For an ordinary single-method request, aim
for roughly 1,000–1,500 English words or comparable detail in another language,
using tables for the required experiment fields. This is a sizing guide, not a
hard limit: expand for greater scientific complexity or an explicitly requested
full protocol. A request for a detailed roadmap still needs concrete controls
and decision rules; it need not contain implementation recipes for every run.
The skill's block template can be expressed as one compact table plus shared
settings while retaining its required information. Finish and verify this core
before optional protocol-level expansion.

Retain the selected skill's required artifacts. Use the user's requested output
paths and existing composition rules; avoid duplicate reports carrying the same
content. A tracker lists runs and statuses, rather than repeating the plan. In standalone
experiment-plan, write the required compact
`refine-logs/EXPERIMENT_TRACKER.md` even when the user chooses another plan
filename. Folding it into a report requires the existing explicit composed-mode
directive; a requested filename alone is not that directive. Before handoff,
check that every required output or referenced record exists.

Finish a usable core artifact before optional expansion. When a time or action
budget is known, reserve capacity to check source calculations, artifact paths,
and required outputs, then deliver the final response. A saved draft is not a
completed session, and a referenced workflow record must actually exist.

Stop when the requested deliverables and checks are complete. A negative result,
an incidental evidence caveat, or an unavailable optional service does not
automatically start another workflow.
